# 死代码清理（可复用流程）

改完一轮代码、或按 README 精简工程之后，用它找出**没有任何地方引用**的顶层定义。
配套 `scripts/deadcode_scan.py`：只用标准库、离线、**只读**（从不改文件）。

```bash
# 扫描：候选目录在前，引用语料根用 --root 指定（默认当前目录）
python <本技能目录>/scripts/deadcode_scan.py <包目录> --root <项目根>
```

退出码：`0` 干净、`1` 有候选（打到 stdout）、`2` 参数或源码树读不了。

## 先想清楚：什么算「被引用」

工具统计的是**纯文本出现次数**，不是调用图。这个选择是刻意的 —— 它让一大类
动态引用**天然安全**，代价是另一类必须显式排除。

| 引用形式 | 例子 | 为什么安全 |
| --- | --- | --- |
| 显式导出 | `__all__ = ["name"]` | 名字就在文本里 |
| 动态取属性 | `getattr(obj, "name")` | 同上 |
| 打包入口点 | `pkg.mod:name`（`[project.scripts]`） | 同上 |
| 前端/模板调用 | `static/app.js` 里的 API 路径 | 前提是 `--root` 覆盖到它 |
| **装饰器注册** | `@app.get("/path")` | **名字不出现，必须显式保护** |

> 所以 `--root` 不要只给包目录：把 `pyproject.toml`、`templates/`、`static/`、
> `scripts/` 都包进语料里，否则前端和打包入口引用的符号会被误判成死代码。

## 唯一的真盲区：装饰器参数注册

```python
@app.get("/evaluate/jobs/{job_id}")
def evaluate_job_status(job_id: str) -> ApiResponse:
    ...
```

这个函数**全项目只出现一次**（就是定义那行），因为路由是靠**路径字符串**登记的，
函数名一个字都没再出现。纯计数判它死刑，一删服务就少一个端点。

**规则：带装饰器的顶层函数一律视为活代码，永不列为候选。** 脚本已内置这条，
连带效果是被它调用的私有 helper（如 `get_evaluation_job`）也因「定义 + 调用 = 2 次」
而安全。

> 这条在实测里救过一次：某包 12 个「零引用」符号中，`evaluate_job_status` 是
> FastAPI 路由，连同 `get_evaluation_job` 必须保留，真实候选是 11 个。

脚本另有一条降噪规则：`__all__`、`__version__` 这类 dunder 赋值**不作为候选**
（它们是模块协议，不是可调用代码），但**仍计入引用**，所以 `__all__` 里列出的
符号照旧受保护。

## 顺带找连锁死代码

删掉一个死函数，常让它独占的 helper 变成新的死代码。所以要**迭代到不动点**：
把已判死的函数从语料里剔除，重算计数，新孤立的一并收进来，循环到没有新增为止。
脚本一次跑完这件事，后续轮次才发现的标 `(chain)`：

```text
pkg/mod.py:24  dead_one
pkg/mod.py:32  dead_two
pkg/mod.py:28  helper_only_for_dead  (chain)
```

真实项目通常第一轮就收敛（没有连锁）；出现 `(chain)` 说明这组函数是自成一体的孤岛，
删的时候整组一起动，别只删一半。

## 动手删的时候

1. **删除前过语法门。** 先 `ast.parse` 校验改完的文本，再落盘 —— 行区间算错一次就是
   整个模块 import 失败。
2. **补回两行空行的间隔。** 删函数要一并吃掉多余空行：前置空行留 2、后置空行留 2，
   否则原地留下 4 连空行，接着被 `ruff format` 改写，白白多出一轮 diff。
3. **保持行尾不变。** 写回时断言文本里没有 `\r`。仓库 `core.autocrlf=true` 时，
   把原本 LF 的 `.py` 写成 CRLF 会让整个文件显示为改动 —— 真实改动被淹没在噪音里。
4. **删完立刻跑 lint。** 死函数往往是某个 import 的**唯一消费者**，删掉它，
   那条 import 就成了新的 F401（本次实测：`defaultdict` 正是被删函数独占的）。别手工找，
   交给工具：

```bash
# 先格式化（删行会打乱空行），再让 ruff 抓出失去消费者的 import
ruff format <路径> --exclude "*.ipynb"
ruff check <路径> --no-fix --no-fix-only --exclude "*.ipynb"
```

5. **复扫确认收敛。** 再跑一次扫描，输出应为 `no unreferenced top-level definition found`。

## 验证：删除也是重构

死代码「没人调用」不等于「删了没影响」—— 它可能被间接测试覆盖、可能共享模块级状态。
所以删除后仍要走完整的验证：

- 静态门：`ruff format` → `ruff check` → `ty check` 全绿（见 SKILL.md「静态检查」）
- 回归测试全过
- **端到端输出逐行比对**：改到输出路径时，把删除前后的 CLI / API 结果 diff 一遍
- 入口点还在：`pyproject.toml` 的每个 `[project.scripts]` 目标都能 import；
  FastAPI 类项目再打一遍路由表，确认端点数量没少

## 判断边界

- **单下划线前缀不算死代码**：`_helper` 是被有意收窄可见性，删之前看是否有同名
  动态引用。
- **同名跨模块会漏报**：两个模块都有 `dead_fn` 且都死时，计数是 2，两条都不会被报出来。
  漏报是安全方向的偏差 —— 宁可漏，不可误删；发现这种情况就手工核对该名字的引用点。
- **不要为了清零而清零**：只被测试引用的符号**不是**死代码（测试是资产）。
  脚本把 `tests/` 算进语料，正是这个意思。

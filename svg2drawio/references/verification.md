# 真机渲染校验

结构自检证明 XML 合法；它证明不了 draw.io 会把图画对。判定依据只有一条：
**用 draw.io 自己渲染一遍，跟原 SVG 的浏览器渲染比对**。

## 1 用 draw.io 导出

draw.io 桌面版自带 CLI，不必开界面：

```bash
draw.io -x -f png --scale 1 -b 0 -o <out.png> <in.drawio>
```

- `-x` 导出而非打开；`-f png` 或 `-f svg`；`--scale` 倍率；`-b` 图片外边距。
- **`-b 0` 必须给**，否则外边距是默认值，等于给对齐再加一个未知量。
- 传绝对路径。Git Bash 里 `/d/...` 不认，用 `D:/...`。
- 单文件 5–30 秒，批量请放后台。

**导出尺寸不等于页面尺寸**：`-b 0` 下得到的是「内容包围盒 + 每边 1px」。
330×210 的页面可以导出成 324×204，也可以成 322×202，取决于内容画到哪。
所以**不要用尺寸去对齐**，见第 2 步。

导出 SVG（`-f svg`）另有用途：里面的 `<image x= y= width= height= viewBox=…>`
是 draw.io 认定的真实几何，读出来跟源图 bbox 对数，比看图准，且不受抗锯齿影响。

## 2 渲染原图并对齐

```bash
chrome --headless --disable-gpu --hide-scrollbars --force-device-scale-factor=1 \
  --window-size=<W>,<H> --screenshot=<orig.png> file:///<abs>.svg
```

`<W>,<H>` 取源图 `viewBox` 的宽高。窗口比页面大留下白边、比页面小截断内容，
两者都会污染差异值。

**对齐靠裁剪，不靠猜偏移**：两边各自去掉白边再比。

```bash
magick in.png -bordercolor white -border 1 -fuzz 2% -trim +repage in-t.png
```

先 `-border 1` 再 `-trim`，是为了让已经贴边的内容不被误裁。裁完两张图的
内容包围盒通常一致（实测同为 322×202）；不一致就说明有一边多了或少了东西，
此时先查原因，不要强行 resize 掩盖。

尺寸仍不一致时统一缩到同宽再比：

```bash
magick a.png -resize 700x a2.png
magick b.png -resize 700x b2.png
```

## 3 算差异——它是分诊，不是判据

```bash
magick compare -metric RMSE a2.png b2.png null:
```

输出归一化到 0–1。以下区间是**实测校准**出来的，不是拍脑袋定的：

| RMSE | 含义 |
| --- | --- |
| < 0.02 | 基本一致。多见于无文字的纯线条图 |
| 0.02 – 0.07 | **含文字图表的正常值**。全部来自字形栅格化差异 |
| 0.07 – 0.12 | 需要看差值图。多半是 1–2px 的整体错位 |
| > 0.12，或局部出现实心亮块 | 结构性缺陷：整块缺失、整体偏移、破图 |

参照点：本包 `assets/sample.svg` 正确转换后约 **0.05**；一页 2255×804、
112 个 cell 的世系图约 **0.035**。所以「0.05 就慌了」是错的——
**0.04–0.05 恰恰是正确结果的常态**。真正的缺陷（丢一个箭头）对这些数字几乎无影响，
这就是为什么第 4 步不能省。

## 4 看差值图，再放大

```bash
magick a2.png b2.png -compose difference -composite -auto-level diff.png
```

判读标准只有一条：**差异是细线还是实块**。

- 通篇只有沿轮廓的一条细线 → 亚像素错位 + 字形栅格化，通过。
- 某处出现实心色块或整块轮廓缺失 → 那里真的少了或多了一块。

细线也可能骗人：一个 12px 的箭头丢了，整图 RMSE 可能只动千分之一，
在差值图上只是一个极小的点。所以对三处必须**定点放大**核对：

```bash
magick orig.png -crop 44x44+<x>+<y> +repage -scale 1000% a.png
magick conv.png -crop 44x44+<x>+<y> +repage -scale 1000% b.png
magick a.png b.png +append ab.png
```

三处是：连接线的折点与端点、箭头尖、旋转单元上的文字。这三样是唯一会**静默**
丢失的东西——框和普通文字面积大，丢了 RMSE 会明显上升；箭头丢了没人报错。

## 5 大图（上千 cell）怎么比

页面到 2500×4200、cell 上千时，RMSE 与裁剪对齐都不够用：裁出来的内容盒子
差 1px 就整体错位，而 1px 错位在这种尺寸上是常态。改用固定倍率 1:1 导出，
再用**整数偏移搜索**对齐：

```bash
draw.io --export --format png --scale 1 --output conv.png conv.drawio
```

导出尺寸**不等于**页面尺寸（2526×4167 的页面导出成 2524×4163），
所以不要拿尺寸对齐，直接搜偏移：

```python
for dy in range(-8, 9):
    for dx in range(-8, 9):
        # 平移后取交集，算 (A&B)/(A|B) 的 IoU，取最大
```

实测参照值：

| 比较对象 | 最佳 IoU | 最佳偏移 |
| --- | --- | --- |
| 重建结果 vs 原始 SVG 渲染 | 0.74 | (-1, -3) |
| 两版独立重建互比 | 0.82 | (0, 2) |

0.74 不是缺陷——差在字形栅格化（真字体 vs 矢量轮廓）和 0.7px 线宽的亚像素渲染。
**判定要靠残差的空间分布**，不看总值：

```python
dA = distance_transform_edt(~ink_ref)
extra = ink_new & (dA > 4)      # 新版多出来的
missing = ink_ref & (dB > 4)    # 新版缺的
```

然后把 `extra` / `missing` 做连通域分析，看**最大连通块**：

- 最大块 < 150px、且集中在文字和细线周围 → 通过，这是抗锯齿残差。
- 出现几百 px 的实块 → 那里真的少了或多了一块。

定位用 20×20 的 IoU 热图（每格单独算交集/并集），低分格子即问题区域，
再按第 4 步定点放大。本包样本 2526×4167 的成图，最差格子在 0.55 左右，
全部来自字形边缘。

**文字基线单独校**：自由文本 cell 的 `y` 是 `baseline − 1.31 × fontSize`
（不是 1.25，也不是字高的一半）。这一项靠渲染行剖面校准：取一小块文字区域，
比较原图与转换结果里"有墨水的行"的起止行号，差 1–2px 才收工。

## 6 没有 draw.io 时

只能做结构自检，并在结论里明写「未做真机渲染校验」。不要拿本包自己的预览图
代替：预览是脚本拼的，走的不是 draw.io 的渲染路径，而两者不一致正是需要这一步的原因。

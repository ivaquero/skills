# 音视频拼接：先探测，再判定，最后才动手

**技能类型**：流程型 —— 工序管「先探测再决定走哪一档」，硬约束管「能 copy 绝不重编」。

合并不是把文件首尾相接。两段素材只要有一项参数对不上，`-c copy` 就会产出无法播放、音画错位或只在第一段就结束的文件；而参数对得上却仍去重编码，则白白损失一整代质量。这个 skill 的全部意义是把「该不该重编、重编哪几段」变成可判定的。

## 铁律

- **参数来自 ffprobe，不来自文件名或印象。** 同一批素材里 `720x1248`、`720x1282` 这种差几个像素的分辨率，或 `44100` 与 `48000` 混排，肉眼看不出，拼起来就是错位。
- **能 copy 绝不重编。** 只有编码或几何/采样率不一致时，重编码才是必要的。
- **重编只编少数派。** 主段保留原始比特流，零代际损失；一个 25 分钟的主段不该为 4 分钟的新片段陪葬。
- **长片一律两阶段：逐段归一化 → 拼接。** 单条 `concat` 滤镜是「一个 N 输入的大流水线」，中断即全废；分段落盘可以随时续。

## 步骤

### 1 探测

```bash
python <this skill dir>/scripts/mmerge.py a.mp4 b.mp4 c.mp4   # 或 a.mp3 b.mp3
```

打印输入分析表、差异检测（逐条标 `OK` / `DIFF` / `info`）、判定结果与确切命令。**默认只打印，不动文件。** 输入全是视频走视频流水线，全是音频走音频流水线；两者混排会直接报错退出——同一轨道里放不下两种内容。

### 2 判定

视频（几何看分辨率、帧率、像素格式、SAR、色彩；编码单独看）：

| 探测结果 | 模式 | 处理 | 代价 |
| :--- | :--- | :--- | :--- |
| 几何、视频编码、音轨**全部一致** | `copy` | concat demuxer + `-c copy` | 零重编码 |
| **仅视频编码不同**，其余一致 | `encode-minor` | 只重编编码不同的那几段 | 只编少数段 |
| 几何或音轨**任一不同** | `normalize` | 逐段等比缩放补边到统一画布 | 全量重编 |

音频（看编码、采样率、声道三元组）：

| 探测结果 | 模式 | 处理 |
| :--- | :--- | :--- |
| 三元组全同 | `copy` | 直接 `-c copy` 拼接 |
| **仅编码不同** | `encode-minor` | 只重编编码不同的那几段 |
| 采样率或声道不同 | `normalize` | 逐段重采样/改声道后拼接 |

判定的关键是把「几何」「编码」分开看：几何决定要不要缩放补边，编码决定要不要重编。混在一起判会把「只有编码不同」误判成全量归一化，白白重编主段。**但音轨不遵循这条**：`-c copy` 要求同一轨道里编码相同，只差音轨时让视频段直接 copy 会产出混编码音轨，所以音轨差异一律升级到 `normalize`。

### 3 执行

```bash
python <this skill dir>/scripts/mmerge.py -o out.mp4 --run a.mp4 b.mp4
python <this skill dir>/scripts/mmerge.py --run a.mp3 b.mp3        # 输出 merged.mp3
python <this skill dir>/scripts/mmerge.py --audio-only --run a.mp4 b.mp4  # 只合并音轨
```

先逐段转码到 `out 同目录/.mmerge-tmp/segs/`，再拼接。中断后重跑会覆盖，已完成的分段不会自动跳过——需要续跑时按区间分批调用，把已完成的段交给 `copy` 档拼接。

输出扩展名不合目标编码时会被自动改正（`-o out.mp4` 合 mp3 会得到 `out.m4a`），因为 mp4 装不下任意音频编码。

### 4 校验

脚本在 `--run` 后会自动读一遍输出，核对编码、时长与体积，并把**成品时长与各源时长之和**对比：偏差超过 `max(0.25 s, 0.5%)` 会标 `WARN`。这一步对音频尤其重要——拼接丢段、AAC priming 累积偏移都只在这里暴露。

视频还要额外做全片解码：

```bash
ffmpeg -v error -i out.mp4 -f null -   # 无输出即无错误
```

这是 `encode-minor` 档的必要门槛，因为两段 SPS 不同时 `-c copy` 会把首段的 `avcC` 套到全片。然后在接缝处抽帧看画面，确认无花屏、黑帧、撕裂。

## 参数怎么定

**视频**：默认 `-c:v libx264 -preset slow -crf 18`，画布取「累计时长占比最大」的那一档，帧率取主帧率并统一转 CFR，时间基从主编码文件读 `time_base` 分母。

**音频**：目标编码按源决定——源全是无损就保持无损（`flac`）；主编码是 mp3 且采样率不超过 48 kHz 就回到 mp3；其余情况统一 `aac`。采样率与声道取各源的**最大值**（升采样不丢信息，降采样会丢）；码率跟住有损源的最高码率并留 25% 余量，夹在 128–320 kbps 之间。

这些选择的依据、实测速度与码率表、以及画布/补边/码率的具体取舍，见 `references/params.md`。

## 坑

真实踩过的，一条一句；细节与复现过程见 `references/casebook.md`。

- **别凭经验估编码时间。** 1080p 全片在 16 线程 CPU 上从「8–15 分钟」估到实际 30 分钟，被中断两次。先在 20 秒样本上量 `speed=`。
- **音频文件里的封面图是「视频流」。** mp3/m4a 常带 `attached_pic`，ffprobe 会报出一条 mjpeg 视频流；不按 `disposition.attached_pic` 跳过，纯音频就被当成视频。
- **raw `.flac` 不接受 `-c copy` 拼接。** 会把首段 STREAMINFO 的块长套到后续数据，解码报 `blocksize 4096 > 1098`，成品只认第一段。改走 concat 滤镜（flac→flac 无损）。
- **`ffmpeg` 打不开输出文件时返回 127。** 看起来像「找不到命令」，实际是父目录不存在。建目录这一步必须先于任何转码。
- **Windows 下 ffprobe 输出是 CRLF。** bash 里 `read` 会把 `\r` 留在值里，`1280\r != 1280`，判定静默失败；用 Python 解析 JSON 则整类问题消失。
- **`[ x -le 30 ]` 不接受 `30.000`。** 浮点帧率进整数比较会报 `integer expected`，用 awk 或 Python 比。
- **`-c copy` 拼接的 profile 取自首段。** 首段是 Baseline，成品就标 Baseline，与后半段实际不符。
- **拼接处的非单调 DTS 警告通常是无害的。** 首段音轨比视频长几十毫秒就会触发，ffmpeg 自动修正；但要在解码校验里确认它没留下真错误。
- **分辨率差几个像素也要补边。** `force_original_aspect_ratio=decrease` 加 `pad` 是唯一不拉伸的做法。

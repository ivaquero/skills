# 案例集：五次真实拼接与踩过的坑

前三个是视频，覆盖三档策略各自成立的条件；后两个是音频，一个是判定，一个是封装边界。数字都是当时的实测值，可直接作为下次的参照。

## 案例一：编码不同，且把耗时估错了（`conquer-1.mp4` + `conquer-2.mp4`）

**探测**：两段都是 1920×1080、30/1 CFR、yuv420p、bt709、tv range、无旋转、AAC 44.1 kHz 立体声、各带一条音轨。唯一差异是编码——一段 H.264 Main L4.0（9.60 Mbps / 629.90 s / 18897 帧），一段 HEVC Main L4.0（7.02 Mbps / 689.83 s / 20695 帧）。

**判定**：`copy` 不成立（同一 mp4 不能混编码），`encode-minor` 也不成立（两段编码互不相同，没有「少数派」可留），只能全量归一化。当时选了单条 `concat` 滤镜一次编码，`-preset medium -crf 19`。

**教训**：**耗时估算错了三倍。** 事前凭经验估「8–15 分钟」，实际 5 分钟才写出 144 MB、35 分钟写到 420 MB，与 ~1.3 GB 的预期体积对照，全程应在 30 分钟以上。任务被中断两次，最终没有产出。

正确的做法是先量：在 20 秒样本上跑 `-f null -`，抓 `speed=`，再乘总时长。这一条现在写进了 skill 的步骤里——`medium` 在 1080p 上只有 0.96×，22 分钟素材就是 23 分钟起步，估成 10 分钟必然崩。

## 案例二：34 段、5 种分辨率、3 种编码（`mil-01` ~ `mil-34`）

**探测**：34 段合计 2 小时 21 分 24 秒、7.39 GB。分辨率有 1080×1920（10 段）、720×1280（20 段）、720×1248（1 段）、720×1282（2 段）、404×720（1 段）；编码 HEVC 26 段、H.264 12 段；帧率全部 30/1 CFR。

按码率与编码习惯还能分成 4 个来源簇：720p HEVC 恒定 5.8–5.9 Mbps 的 22 段、720p H.264 High 8.2 Mbps 的 3 段、1080p H.264 Main 9.7 Mbps 的 5 段、1080p HEVC 7.1 Mbps 的 5 段。**同一批命名连续的素材来自不同设备，是常态。**

**判定**：几何参数不一致，只能 `normalize`。选 1080×1920 画布，`veryfast` + CRF 20。

**做法**：两阶段。逐段归一化到 `.mil-merge/segs/`，再 `concat` demuxer 拼接。中途被中断在第 10/11 段，**已落盘的 10 段可以直接复用**，这正是选两阶段而不是单条滤镜的理由。实测 39 分钟素材 12 分钟转完，约 3.2×，与基准的 3.56× 吻合（略低是因为其中一段要从 404×720 放大，滤波开销占比更高）。

**三个具体坑**：

1. `mil-01`（720×1248）、`mil-05`/`mil-11`（720×1282）比例不是 9:16，直接缩放会变形，必须补边。
2. `mil-10` 是 404×720 的唯一低清段，放大到 1080×1920 后必然偏软——这是源的信息量问题，调参数补不回来。
3. 中断后恢复前，**必须先确认分段文件还在**。那次重跑时整个工作目录已经不在原处，脚本「已存在就跳过」的逻辑会从零开始；而残留的半截 mp4 如果没有 moov，`ffprobe` 读不出时长，被当成成品拼进去就会在开头断帧。**校验手段**：对每个分段跑一次 `ffprobe -show_entries format=duration`，读不出时长的一律删除。

## 案例三：只重编 4 分半（`family.mp4` 追加到 `ygdj-family-merged.mp4`）

**探测**：主段 24 分 29 秒、H.264 High L4.0、5.14 Mbps、timescale 1/15360；新段 4 分 22 秒、HEVC L4.0、5.62 Mbps。两者都是 1920×1080、30 fps、yuv420p、bt709、AAC 44.1 kHz 立体声。**几何全同，只有编码不同。**

**判定**：`encode-minor`。把 4 分 22 秒的 HEVC 转成 H.264（CRF 18 + slow，实测输出 4.48 Mbps，与主段 5.14 Mbps 同档），主段 24 分 29 秒的原始比特流原封不动，然后 `-c copy` 拼接。

**结果**：51 915 帧（44 067 + 7 848）、1730.63 s（1468.99 + 261.62）、1.13 GB，总耗时约 4 分钟——**比全量重编省下约半小时**。

**校验做了两件事**：

1. 全片解码 `ffmpeg -v error -i out.mp4 -f null -`，零输出。这一步是 `encode-minor` 的必查项：两段 SPS 不同，`-c copy` 只写首段的 `avcC`，后半段实际靠解码器的容错能力过关。同分辨率同 profile 时实测无损，但这是**实测结论而非保证**，换素材必须重验。
2. 接缝处抽帧（1468.5 s 与 1470 s）确认画面正常，无花屏、黑帧、撕裂。

**两处需要知道的输出特征**：

- 成品的 `profile` 标签取自首段。首段是 High，输出就标 High，与后半段实际编码参数无关。
- 拼接时报了一条 `Non-monotonic DTS; previous: 64782461, current: 64782373`，发生在 1468.99 s（音频时间基 44100 下正好是接缝）。原因是首段音轨比视频长 21 ms，回退约 2 ms，ffmpeg 自动修正。**听不出来，也不影响同步**，但要知道它为什么出现。

## 案例四：音频四段、三种签名（`a.mp3` / `b.mp3` / `c.m4a` / `d.wav`）

**探测**（合成样本，各 4 秒）：`a.mp3`、`b.mp3` 是 mp3 44.1 kHz 立体声 128k；`c.m4a` 是 aac 44.1 kHz 立体声 128k；`d.wav` 是 pcm_s16le 48 kHz **单声道** 768k。`bitrate` 一列被明确标成 `info` 而非 `DIFF`——码率不同不构成重编理由，采样率与声道才构成。

**三档判定各自成立**：

| 输入 | 判定 | 目标 | 实测 |
| :--- | :--- | :--- | :--- |
| a + b | `copy` | mp3 流拷贝 | 8.05 s（源 8.00） |
| a + c | `encode-minor` | 只把 c.m4a 转成 mp3 160k | 8.05 s |
| a + d | `normalize` | 全部重编 mp3 160k @ 48 kHz 立体声 | 8.05 s |

`encode-minor` 的 160k 来自「源最高有损码率 128k × 1.25」。单声道那条被升到立体声、44.1k 被升到 48k——都与「取最大值」的规则一致。

**一致的 +0.05 s 偏差不是 bug**：mp3 每段带约 1152 个采样的编码器延迟，两段就是 ~52 ms。它不会累积成音画不同步，因为视频侧拼的是同一批源；但如果拼接的是「静音间隔很重要」的材料（如音乐专辑），要知道每个接缝处有几十毫秒的余量。

## 案例五：flac 拼接只出一半

**现象**：两段 4 秒的 flac 走 `-f concat -c copy` 拼接，命令报告写入 `time=00:00:08.00`、体积 130 KiB（约 8 秒的数据量），但 `ffprobe` 读出的时长是 **4.0 s**，`nb_read_frames` 只有 175 帧（一段的量），解码时满屏：

```text
[flac @ ...] blocksize 4096 > 1098
[flac @ ...] decode_frame() failed
```

**原因**：raw `.flac` 是「一个文件一个 STREAMINFO」的裸流封装，没有时间戳也没有多段拼接的概念。`-c copy` 把首段的 STREAMINFO（含块长 4096、总采样数）写在最前面，后续数据按不同块长写入，解码器按首段的块长去切，切到第二段就崩。**数据其实都写了，只是头信息与实际内容不符。**

**验证过程**：同一份分段，换成 `.mka` 封装得到 8.000 s；用 `concat` 滤镜重编得到 8.000 s 且解码零错误。两者都正确，说明问题只出在「raw flac + copy」这个组合上。

**处理**：`mmerge.py` 判到目标编码是 flac 时，自动把最后一步换成 `concat` 滤镜重编（flac 对 flac 是无损的），并把 `list_file` 置空——不再写那份用不上的清单。这条已固化为 `selfcheck.py` 里的一项：两段 flac 拼接后必须 4 s 且解码零错误。

## 案例六：封面图让纯音频变成「视频」

mp3、m4a、flac 都可以内嵌封面，ffprobe 会把它报成一条 `codec_type=video`、`codec_name=mjpeg` 的流。第一版 `probe()` 取「第一条视频流」就判定为视频，于是带封面的 mp3 被送进视频流水线，随后在 `-vf scale=...` 上报错。**修法是看 `disposition.attached_pic == 1` 跳过**，而不是猜编码名。

这个坑还牵出一个副作用：`-c copy` 拼接时若不显式 `-map 0:a:0`，默认流选择会把封面当视频流映射进输出，成品会「挂着」第一段的封面。音频流水线的拼接命令因此固定带 `-map 0:a:0`。

## 通用坑清单

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| `ffmpeg` 返回 127，像「找不到命令」 | 输出文件的父目录不存在（如 `segs/` 未建） | 转码前无条件 `mkdir -p`；不要把 127 一律当环境问题 |
| 纯音频被判成视频 | 内嵌封面是 mjpeg 视频流 | 按 `disposition.attached_pic` 跳过 |
| flac 拼接只认第一段 | raw flac 不接受 copy 拼接，STREAMINFO 与数据不符 | 改走 concat 滤镜重编 |
| 拼接后每段之间多几十毫秒 | mp3/aac 每段的编码器延迟与 priming 样本 | 时长偏差校验；音乐类素材需在软件里重新对齐 |
| bash 里分辨率比较静默失败 | Windows 下 `ffprobe` 输出 CRLF，`read` 把 `\r` 留在值里（`1280\r != 1280`） | 解析后 `v="${v%$'\r'}"`；改用 Python 读 JSON 则整类问题消失 |
| `ffprobe: Impossible to open '/c/Users/...'` | ffmpeg 是原生 Windows 程序，不认 MSYS 的 `/c/...` | 转成 `C:/Users/...`（正斜杠可用，不必转反斜杠） |
| `[: 30.000: integer expected` | `[ -le ]` 只接受整数，而帧率是浮点 | 用 awk 或 Python 比 |
| Markdown 表格/终端表格列错位 | `printf %-11s` 按字节计宽，中文占 3 字节算 1 个字符 | 表头改 ASCII，或按显示宽度手工补 |
| `Unknown cover type: 0x1` | `.mov` 容器里带封面图元数据 | 无害，忽略 |
| 分段 mp4 无法探测 | 转码中断，moov 未写入 | 拼接前逐段校验时长，失败即删 |
| 首次 `concat` 报 `Non-monotonic DTS` | 首段音轨比视频长几十毫秒 | 通常无害，以全片解码校验为准 |

## 一条流程性的经验

**先用区间分批跑，再合并。** 案例二把 34 段分成 `01–11`、`12–25`、`26–34` 三组，每组单独出片。好处是三组可以分别验收、分别重来，任意一组出问题不会牵连另外两组。代价只是多两次拼接，而拼接是 `-c copy`，几秒的事。

这条现在已经固化成 `--groups 1-11,12-25,26-34`：三组各自判定模式、各自出片，中间目录按组分开（`.mmerge-tmp/01-11/`），互不覆盖。分组边界不是随便切的——它该落在参数簇变化处，也就是表里「编码/分辨率/帧率连续相同」的那一段结束的位置。

反过来，一开始就上「一个命令拼 34 段」的做法，在中断一次之后就没有第二次机会了。

音频这边同样适用：一次合并 40 集有声书时，按 10 集一组出片，远比一次喂进 40 个输入安全——尤其 flac 那一档最后一步是滤镜重编，整条流水线是单进程的。

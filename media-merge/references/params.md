# 参数选择依据

写这份文档的目的，是让下一次不必重新试探。视频部分的数字是在 16 线程 CPU、无 GPU 的 Windows 机器上实测得到的；换机器绝对值会变，但相对关系稳定。音频编码速度的量级差异太大，只用来说明「不必为音频的耗时为难过」。

## 视频：目标编码为什么是 H.264

三选一：

| 编码 | 编码耗时 | 体积 | 兼容性 |
| :--- | :--- | :--- | :--- |
| H.264 | 1× | 1× | 浏览器、播放器、社交平台全通 |
| HEVC | 2–3× | 约 0.7× | 部分网页与播放器不支持 |

拼接场景里编码耗时是主导因素：一次拼接往往要处理几十分钟素材，选 HEVC 会让「等一小时」变成「等三小时」，换来的只是体积小 30%。除非播放环境明确支持 HEVC 且体积是第一约束，否则统一到 H.264。

硬件编码（`h264_nvenc` / `hevc_nvenc`）在有 NVIDIA GPU 时速度快 5–10 倍，但同码率下画质明显逊于 `libx264`，且不支持 `-crf` 的恒定质量语义（要用 `-cq`）。有 GPU 且只求快时可用，需要画质时仍走 `libx264`。

## 视频：preset 与 CRF

实测于 1080p30 素材，20 秒样本，取稳态 `speed=`：

| preset | 速度 | CRF | 视频码率 |
| :--- | :--- | :--- | :--- |
| veryfast | 3.56× | 20 | 4043 kb/s |
| fast | 1.24× | 20 | — |
| medium | 0.96× | 20 | 3239 kb/s |
| medium | 1.08× | 18 | 4165 kb/s |
| slow | 1.48× | 18 | 3918 kb/s |
| slow | 0.81× | 20 | 3041 kb/s |

720p 素材（1280×720）在 `veryfast` 下可达 6.89×，`fast` 3.89×——**分辨率除以 2.25，速度大约翻倍**，这是估算其他尺寸的锚点。

选 **CRF 18 + slow**：压缩效率最好，码率与常见 H.264 源（5 Mbps 量级）同档，接缝处不会出现画质台阶。CRF 18 相对 20 的码率增幅约 30%，对一次性拼接可以接受。

注意 `slow` 与 `medium` 的速度差在实测里并不单调（1.48× 对 1.08×），这是线程调度与解码争用带来的噪声。真实取舍是：两者都在 1× 上下，都能接受。要快就用 `veryfast`，代价是码率涨三成。

**耗时估算**：`总时长 ÷ speed`。1080p `veryfast` 约 3.5×，即 60 分钟素材约 17 分钟；`slow` 约 1.5×，即 40 分钟。先算这个数，再决定要不要跑——**估错一次就是白等半小时**。

## 视频：画布按时长占比取多数派，不取最大

一段 24 分钟的 1080p 加一段 4 分钟的 720p，画布该选哪个？按「最大分辨率」选 1080p 会让那 4 分钟上采样（无细节增益，只是文件更大）；按「总时长占比」选 1080p 则四分之三的素材原生匹配。

`mmerge.py` 用的是**累计时长占比最大**的那一档。这是唯一同时照顾「多数素材原生」与「少数素材不变形」的规则。若素材是竖屏为主、混入几段横屏，则应显式指定画布（`-c 1080x1920`），让横屏段补边，而不是让多数段被裁。

同一份素材的两种画布实测（141 分钟素材）：

| 画布 | 耗时 | 体积 |
| :--- | :--- | :--- |
| 1080×1920 | 40 分钟 | 约 4.5 GB |
| 720×1280 | 20 分钟 | 约 1.9 GB |

体积与耗时都约等于按像素数等比缩放，可以直接外推。

## 视频：补边是不拉伸的唯一做法

```text
scale=W:H:force_original_aspect_ratio=decrease:flags=bicubic,
pad=W:H:(ow-iw)/2:(oh-ih)/2:color=black,
setsar=1,fps=<主帧率>,format=yuv420p
```

`decrease` 保证整幅画面进得去，`pad` 把空出来的部分补黑，居中。常见比例不匹配的补边量：

| 源 | 目标 1080×1920 | 补边 |
| :--- | :--- | :--- |
| 720×1280 (9:16) | 1080×1920 | 无，等比放大 1.5× |
| 720×1248 | 1080×1920 | 上下各 28 px |
| 720×1282 | 1080×1920 | 左右各 1 px |
| 404×720 | 1080×1920 | 放大约 2.7×，画质必然偏软 |

最后一行说明一件事：**补边能解决比例，解决不了信息量**。低清段放大后偏软是源的问题，调参数补不回来，需要提前告知。

## 音频：目标编码按源决定，不做降级

三档，按顺序匹配：

| 条件 | 目标 | 理由 |
| :--- | :--- | :--- |
| 源全部无损（flac/alac/wav 的 `pcm_*`） | `flac` | 无损进无损出，不制造一代损失 |
| 主编码是 mp3 且采样率 ≤ 48 kHz | `mp3` | 元数据、播放器习惯都保持原样，用户拿到手不用换工具 |
| 其余 | `aac` | 同码率下优于 mp3，采样率上限也够高 |

把无损源压进有损是最容易犯的错：体积只小一半，信息却是永久丢掉。`mmerge.py` 判到「全部无损」就直接把目标钉成 flac，不给这个选项。

反过来，主编码是 aac 时也不会「顺手换成 mp3」——那同样是一次跨编码代际损失，而且用户的播放器本来就用得好好的。

## 音频：采样率与声道取最大值

三段 44.1 kHz 加一段 48 kHz，目标取 **48 kHz**，不是多数派的 44.1。

升采样（44.1→48）只是重采样插值，不丢信息；降采样（48→44.1）会削掉 22.05 kHz 以上的内容。多占的体积微不足道，所以永远选大的一侧。声道同理：单声道升立体声是复制，立体声降单声道是永久丢失。

## 音频：码率跟住有损源，不跟无损源

```text
base = max(有损源的 bit_rate) × 1.25
mp3  夹到 128–320 kbps
aac  夹到 128–256 kbps
```

两个要点：

- **×1.25 是给重采样/混音留的余量。** 同码率重编一次会掉一档，略高的目标码率能把这部分补回来，同时不至于把 128k 的源吹成 320k。
- **WAV 的「码率」不算数。** 48000 Hz × 16 bit × 单声道 = 768 kbps，那是 PCM 的裸速率，不是压缩质量。早期版本把它算进去，结果把 128k 的 mp3 重编成 320k——体积涨 2.5 倍，信息一点没多。现在只统计有损源。

## 音频：copy 的边界

`-c copy` 能不能拼接，取决于封装能否容纳「首尾相接的独立帧」，与编码本身无关：

| 封装 | `-c copy` 拼接 | 说明 |
| :--- | :--- | :--- |
| mp3 | 可以 | 帧自包含，实测 8 s 输入得 8.05 s，多出的是编码器延迟 |
| m4a / aac | 可以 | 少量 priming 样本留在接缝处，±50 ms 量级 |
| wav | 可以 | 头信息由 muxer 重写，时长准确 |
| ogg / opus | 可以 | 实测 8 s 得 8.02 s |
| **flac（裸流）** | **不可以** | 首段 STREAMINFO 的块长会套到后续数据，解码报 `blocksize 4096 > 1098`，成品只认第一段 |

flac 因此改走 `concat` 滤镜重编：flac 对 flac 重编是无损的，代价只是多一次编解码，而 flac 编码速度在数百倍实时，实际感受不到。

## 音频：为什么不必为耗时为难过

音频编码的吞吐比视频高两个数量级：`libmp3lame`、`aac`、`flac` 在 1 小时单声道素材上都是分钟级甚至秒级完成，瓶颈通常在磁盘 I/O 而不是 DSP。所以音频这边**不必像视频那样为了速度降低质量**——CRF/preset 那套取舍只适用于视频。这也是为什么音频的默认值直接取了偏保守的一侧（flac `-compression_level 8`、mp3 320k 上限、aac 256k 上限）。

## 分组：组间一致与组内原生的取舍

一批素材按区间分成几组时，画布该「每组各算」还是「全局统一」？答案是看下游：

| 策略 | 画布 | 代价 |
| :--- | :--- | :--- |
| 各组自算（默认） | 每组按本组累计时长占比最大的那档 | 组间可能不同，成片不能再直接拼 |
| `--uniform` | 全部输入按同一规则算出的一套 | 少数派那组被上/下采样 |

`--uniform` 的代价不对称：`1080p` 组被拉到 `720p` 是真掉信息，`720p` 组被拉到 `1080p` 只是变大、细节不会回来但也不损失。所以当分组里混着 `1080p` 与 `720p`，而目标是要拼成一条时，宁可让 720p 组上采样——这也是 `mil-*` 那批最终选 `1080×1920` 而不是 `720×1280` 的原因之一。

音频的 `--uniform` 同理：采样率与声道按全局最大值取，短的那组会被升采样，不丢信息但体积略增。

## 为什么是两阶段而不是单条 concat 滤镜

| 做法 | 命令形状 | 中断代价 |
| :--- | :--- | :--- |
| 单条 `concat` 滤镜 | 一个命令，N 个输入 | 全废，从头再来 |
| 逐段归一化 + 拼接 | N 个短命令 + 一个拼接 | 只丢当前那一段 |

后者还有两个附带好处：每段转码可以单独复核，出问题能定位到具体素材；拼接是纯 copy，几秒完成，可以反复重来。代价是多一次磁盘读写和中间文件占位。对超过十分钟的素材，这个交换永远值得。

唯一的例外就是 flac 拼接——它必须用 concat 滤镜，因为 raw flac 封装不接受 copy 拼接。这一档的中间文件仍然逐段落盘，可以单独复核，只是最后一步不是 copy。
